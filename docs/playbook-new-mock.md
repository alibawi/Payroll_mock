## 1. الهدف وما هو خارج النطاق

- **الهدف**: موك أب تفاعلي بمظهر "نظام حقيقي" (loading/error states، فلاتر، فورمات، state machines) لعرضه على عملاء/مستثمرين والتحقق من تجربة الاستخدام قبل بناء الباك إند.
- **خارج النطاق**: أي باك إند حقيقي، مصادقة حقيقية، حفظ دائم. كل البيانات وهمية من JSON محلي، وكل "حفظ" يحدّث حالة محلية فقط.
- أي تكامل مع أنظمة خارجية (مثلاً ERP) يُعرض كـ Placeholder تفاعلي فقط.

## 2. التقنيات (ثابتة)

- **Next.js (App Router) + TypeScript**
- **Tailwind CSS** (ملاحظة: v4 لا يستخدم `tailwind.config`، التوكنز عبر CSS variables + `@theme inline` بـ`globals.css`)
- **shadcn/ui** (إضافة مكوّنات عبر `npx shadcn@latest add <component>`)
- `next-themes` للوضع الفاتح/الغامق، `lucide-react` للأيقونات

## 3. هيكل المجلدات

```
app/
  (shell)/          # كل الصفحات اللي تحتاج Sidebar/Topbar — بما فيها كل مجلدات الموديولات
    dashboard/
    <module>/
  login/            # خارج (shell)
  api/              # Route Handlers لكل الـ Mock API
mock-data/          # ملفات JSON — مصدر الحقيقة الوحيد للبيانات الوهمية
components/         # مكوّنات مشتركة فقط
  ui/               # shadcn
  shell/            # Sidebar, Topbar, Breadcrumbs, RoleSwitcher
lib/                # mock-api.ts, i18n/labels.ts, navigation.ts, types, permissions
docs/               # roadmap + spec-*.md + prompts-*.md
```

> **مهم**: مجلدات الموديولات لازم تكون **داخل** `app/(shell)/` (مو جنبه). الـ`layout.tsx` جوة route group ما يلف إلا اللي بداخله. هذا الخطأ صار بمشروع ENKI وانصلح — لا تكرره.

## 4. القواعد الإلزامية (تنكتب حرفياً بـ CLAUDE.md)

1. **إعادة استخدام المكوّنات**: كل موديول يستخدم `components/` المشتركة. تنويع مطلوب → وسّع المكوّن المشترك بـprops، لا تكرره. ممنوع مكوّنات UI عامة داخل `app/<module>/`.
2. **البيانات الوهمية عبر API فقط**: JSON بـ`mock-data/` تُقرأ حصراً عبر `app/api/`. الصفحات تسوي `fetch` ولا تستورد JSON ولا تكتب arrays ثابتة داخل الكومبوننتات.
3. **نمط الشاشات الخمس لكل موديول**: لائحة → تفاصيل → إنشاء/تعديل → سجل حركات → مؤشرات صغيرة.
4. **Dark/Light + RTL/LTR تلقائياً**: ألوان بـtokens دلالية فقط (`bg-card`, `text-muted-foreground`...) بدون hex مباشر بالمكوّنات، وخصائص منطقية (`ps-`/`start-`/`text-start`) بدل `pl-`/`left-`.
5. **WORKLOG.md**: قبل أي عمل اقرأه من البداية. بعد كل مهمة أضف سجلاً بالأسفل (Append-only، ممنوع تعديل/حذف القديم).
6. **بيانات واقعية ومترابطة**: أسماء وجهات وتواريخ وأرقام كتب واقعية (مو Test1/Test2)، وكل كيان يشير للثاني بمعرّف (`employeeId`, `correspondenceId`...).
7. **commit صغير لكل شاشة** بصيغة `feat(<module>): <وصف>` (أو `chore:`/`docs:`/`fix:`).

## 5. القيود التقنية المعروفة (وفّرنا عليك الوقت)

- **لا تلف مكوّن `Button` المشترك داخل `render`/`asChild` لـ Base UI** (`DropdownMenuTrigger`, `Link`...) — يطلع تحذير "expected a native button". استخدم عنصر خام (`<button>`/`<Link>`) مع `buttonVariants` كـclassName.
- شعار بنص أسود: ضعه دائماً داخل بطاقة `bg-white` ثابتة حتى يبقى مقروء بالوضع الغامق.
- `next-themes`: `enableSystem={false}` و`defaultTheme="light"`، و`suppressHydrationWarning` على `<html>`.
- `<html>` الافتراضي `lang="ar" dir="rtl"` لتفادي الوميض.
- تبديل الخط بحسب اللغة عبر `--font-sans` (`[dir="ltr"]` override).
- اختياري: سكربت `dev` ينظّف `.next` قبل التشغيل لتفادي مشاكل الكاش.

## 6. مراحل العمل

### المرحلة أ — التخطيط (أنت تكتبه، المستخدم يراجعه)

1. اقرأ الوصف الفني **كاملاً**.
2. اكتب `docs/roadmap.md`: الموديولات، القرار المعماري، هيكل المجلدات، **ترتيب البناء حسب الترابط** (الأساس والمدخل الأسهل للزبون أولاً، ثم اللي يعتمد عليه، والموديولات العابرة كـWorkflow/Access Control/Analytics آخراً)، وتقدير زمني.
3. لكل موديول اكتب `docs/spec-<module>.md` **مستخرج من قسمه بالوصف الفني** (ما تخترع شي مو موجود بالمصدر). أقسام الـSpec الثابتة:
   - نطاق الموديول وصلته بالموديولات الثانية
   - نموذج البيانات (جداول حقول)
   - دورة حياة الحالات (State Machine)
   - قواعد العمل (Business Rules) — كجدول قابل للتطبيق كـvalidation
   - الصلاحيات
   - مؤشرات لوحة الموديول (KPIs)
   - التكاملات (Placeholders)
   - **قائمة الشاشات الكاملة** (قسم يُستخدم مرجع تنفيذي)
   - **ترتيب الأوامر** للبناء
4. لكل موديول اكتب `docs/prompts-<module>.md`: برومتات مرقّمة (`N.1`, `N.2`...) بصيغة القالب بالقسم 8، كل برومت يشير لأرقام أقسام محددة بالـSpec.
5. **قف هنا** وأعرض على المستخدم: قائمة الموديولات + الترتيب + ملخص كل Spec. لا تكمل قبل موافقته.

## 7. آلية التحقق (لكل تغيير مرئي)

لا تعتمد على "الكود يبدو صح". بعد كل شاشة:
1. شغّل الـdev server (`preview_start`) وافتح الصفحة.
2. راجع الـconsole والـnetwork (صفر أخطاء/تحذيرات).
3. جرّب التفاعل (فلاتر، أزرار، مودالات) وتأكد من النتيجة.
4. بدّل الثيم واللغة وتأكد من الاتجاه والقراءة.
5. `npm run build` لازم ينجح قبل الـcommit.
6. اذكر بالـWORKLOG شنو تحققت منه فعلياً.

## 9. صيغة سجل WORKLOG

كل سجل يحتوي: **التاريخ · الموديول/الشاشة · المُنجز (بدقة) · قرارات تصميمية مهمة (خصوصاً اللي خالفت/وسّعت الـSpec) · مشاكل/مؤجّل · التحقق الفعلي · الخطوة الجاية**. سجّل أيضاً أي انحراف عن الـSpec أو الرود ماب مع السبب.
